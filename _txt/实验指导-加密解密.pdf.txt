1. 为什么备份软件需要加密
 
在之前的课程中，我们已经实现了：
文件遍历与过滤（CFileEnumerator ）
打包解包（CMyPack ）：将目录树合并为一个大文件
压缩解压（CHuffman  / CLZ77 ）：减小备份文件的体积
但此时备份文件存在一个严重的安全隐患：任何能够访问该文件的人，都可以直接解包还原出所有原始数据。
试想以下场景：
备份文件存储在移动硬盘或U盘中，设备丢失
备份文件上传到云端存储服务
备份文件存放在共享服务器上，被非授权用户访问
加密的目的就是：即使备份文件落入他人之手，没有正确的密码也无法还原任何数据。
加密算法分为两大类：
本项目采用对称加密，因为：
备份场景中只有一个用户（或一组共享密码的用户）需要访问数据
对称加密速度远快于非对称加密，适合加密大量数据
实现相对简单
2. 密码学核心概念扫盲
 
本讲义不涉及复杂的数学原理（如S盒、置换表、椭圆曲线等），仅解释在代码中直接出现的关键概念。

2.1 分组密码与流密码
 
流密码（Stream Cipher）：
逐字节或逐比特加密
每个位置的明文用不同的密钥流加密
优点：无需补齐，实时性强
缺点：如果密钥流重用，容易被攻击
分组密码（Block Cipher）：
将明文分成固定大小的块，逐块加密
DES：每块 8字节（64位）
AES：每块 16字节（128位）
本项目使用的 DES-EDE-CBC 和 AES-256-CBC 都属于分组密码
2.2 什么是CBC模式（密码分组链接）
 
分组密码有多种工作模式，CBC（Cipher Block Chaining）是最常用的一种。
核心思想：每个明文块在加密前，先与前一个密文块进行异或（XOR）运算，然后再加密。
CBC模式的两个关键点：
1. 初始化向量（IV）：第一个块没有“前一个密文块”，因此需要一个随机的IV。即使两份完全相同的明文使
用相同密钥加密，只要IV不同，密文就完全不同。
2. 错误传播：如果某个密文块损坏，会导致两个明文块出错（当前块和下一块）。但在备份场景中，我们更
关注数据完整性（CRC64校验）而非实时传输，这是可以接受的。
2.3 数据补齐（Padding）
 
分组密码要求输入数据长度必须是块大小的整数倍。
DES：块大小 = 8字节，数据长度必须是8的倍数
AES：块大小 = 16字节，数据长度必须是16的倍数
PKCS#7补齐规则：
加密过程：
  密文块0 = 加密(明文块0 ⊕ 初始化向量IV)
  密文块1 = 加密(明文块1 ⊕ 密文块0)
  密文块2 = 加密(明文块2 ⊕ 密文块1)
  ...
解密过程：
  明文块0 = 解密(密文块0) ⊕ IV
  明文块1 = 解密(密文块1) ⊕ 密文块0
  明文块2 = 解密(密文块2) ⊕ 密文块1
  ...

为什么使用盐值（Salt）？
HASH_SALT  定义为 "databackup-uestc" 。盐值的作用是防止彩虹表攻击。
攻击者可能预先计算常用密码的哈希值（彩虹表），用于快速破解。
加盐后，即使两个用户使用相同密码，哈希结果也完全不同（因为盐值可能不同，这里盐值固定但已足够
防止通用彩虹表）。
盐值不应该是秘密的，它可以明文存储在代码中。它的作用是增加攻击者的计算成本。

为什么不直接用 hash1  同时做密钥和验证？
如果直接把 hash1  存入文件头用于验证密码，攻击者可以读取文件头的 hash1 ，虽然无法逆推出原始密码，但 
hash1  本身就可以作为密钥使用（因为加密密钥就是从 hash1  切出来的）。这意味着攻击者不需要知道原始密码，
只要拿到文件头里的 hash1  就能解密数据。
使用 hash2  作为验证凭证，而加密密钥来自 hash1 ，两者分开，攻击者即使读取了文件头的 hash2 ，也无法推
算出 hash1  和加密密钥。

    std::string hash2 = this->saltedSHA256(hash1);
    
    // 7. 比对 hash2 是否与文件头中存储的一致
    if (hash2 != std::string(ehs.key, FILE_ENCRYPO_KEY_LENGTH)) {
        return ENCRYPT_KEY_ERROR;  // 密码错误
    }
    return 0;
}

为什么 DES 没有显式指定 IV？
在 EVP_EncryptInit_ex  中，如果 IV 参数传 NULL ，OpenSSL 会使用全零 IV。在 CBC 模式下，全零 IV 本身并
不安全（相同明文的第一个块会产生相同密文），但由于 DES 在本项目中已不推荐使用，代码保留了这种简化写法。
强烈建议学生使用 AES 并显式指定 IV。

在课堂演示时，可以这样向学生解释选择：

7. 封装成库与ABI兼容性
 
7.1 为什么要封装成库
 
在大型软件工程中，核心逻辑与界面实现分离是重要的设计原则：
界面层：可以使用 Qt、MFC、.NET 等技术，专注于用户体验
核心层：使用 C/C++ 编写，专注于算法性能和稳定性

这样做的好处：

3. 单元测试：核心库可以独立进行测试
4. 复用性：同一个核心库可以被不同的界面程序使用（命令行、GUI、Web服务）

C++ 标准没有规定 ABI，这意味着：
GCC 编译的 C++ 库与 Clang 编译的 C++ 程序可能二进制不兼容
不同版本的 GCC 生成的 C++ 代码可能不兼容
不同操作系统上的 C++ ABI 差异更大

名称修饰（Name Mangling）：

标准库差异：
std::string  的内存布局在不同编译器间可能不同
异常处理的实现机制可能不同

9.2 为什么先压缩后加密
 
这是一个重要的工程决策。必须压缩后再加密，顺序不能颠倒。
原因：
压缩算法（如 LZ77 和 Huffman）依赖数据中的冗余来实现压缩：
重复的字符串（LZ77）
不均匀的字符频率（Huffman）
加密算法的输出是伪随机数据：
每个字节出现的概率近似相等（无法用 Huffman 压缩）
几乎没有重复模式（无法用 LZ77 压缩）
如果将加密后的数据再压缩，压缩率将非常低（接近 1:1），浪费了计算资源。
正确顺序：
错误顺序：

10.1 需求背景
 
在实际使用中，用户需要确认备份文件是否完整可用。可能出现的问题：
备份过程中系统崩溃，文件不完整

10.2 最简单的实现方案：CRC
 
CRC（Cyclic Redundancy Check，循环冗余校验） 是一种常用的错误检测码。
在备份场景中的用法：
1. 打包/压缩/加密完成后，计算整个文件的 CRC64 值
2. 将 CRC64 值存入文件头（commonHeaderStruct.CRC64 ）
3. 验证时重新计算文件的 CRC64，与存储的值比对
4. 一致则表示文件完整，不一致则表示文件已损坏
用户操作: 选择备份文件 → 输入密码 → 点击"开始还原"

10.3 代码中的 CRC64 实现
 
updateFileCRC64  的工作原理：
1. 读取目标文件的所有数据
2. 计算 CRC64 值
3. 将值写回到文件头的 CRC64  字段
checkFileCRC64  的工作原理：
1. 读取文件头的 CRC64  存储值
2. 计算整个文件（除 CRC64 字段自身）的 CRC64 值
3. 比对两者是否一致
10.4 CRC 的局限性
 
需要向学生说明 CRC 的适用范围：
CRC 能检测意外错误（传输错误、存储介质损坏）
CRC 不能防止恶意篡改（攻击者可以同时修改数据和 CRC 值）
如果需要防篡改，应使用数字签名（如 RSA + SHA256）
在备份场景中，CRC 足以应对磁盘损坏、文件系统错误等常见问题。
11. 课堂思考题
 
思考题1
 
问题：为什么代码中要保存 hash2  到文件头用于验证密码，而不是直接保存 hash1 ？
参考回答：如果保存 hash1 ，攻击者即使不知道原始密码，拿到文件头中的 hash1  后，因为加密密钥就是从 
hash1  截取的（hash1.substr(0, 32) ），可以直接用 hash1  解密数据。保存 hash2 （hash1  的哈希）做验
证，攻击者无法从 hash2  反推出 hash1 ，更无法反推出原始密码，安全性更高。
// 在 encrypt 函数末尾
if (updateFileCRC64(targetFile) < 0) {
    std::cout << "更新文件CRC64时失败: " << targetFile << std::endl;
    return -1;
}
// 在 decryptionCheck 函数中
if (checkFileCRC64(file) < 0) {
    std::cout << "文件CRC64校验失败: " << file << std::endl;
    return BACKUP_DATA_FILE_ERROR;
}

思考题2
 
问题：如果用户输入的密码是 "123456" ，加密后的文件头中 key  字段的值是什么格式？包含数字和字母吗？
参考回答：key  字段存储的是 hash2 ，即经过两次 SHA-256 哈希后得到的 64 个字符的十六进制字符串（只包
含 0-9 和 a-f）。完全不包含用户原始密码的任何信息。
思考题3
 
问题：为什么必须“先压缩后加密”？如果反过来“先加密后压缩”会怎样？
参考回答：加密后的数据近似随机，没有冗余结构，压缩算法几乎无法压缩（压缩率接近 1:1），白白浪费了 
CPU 时间。所以正确顺序是压缩 → 加密。
思考题4
 
问题：代码中 DES 没有显式指定 IV，AES 显式指定了 IV。这种差异会导致什么安全问题？
参考回答：DES 使用全零 IV，如果两份完全相同的明文使用相同密钥加密，密文的前 8 字节会完全相同，攻击者
可以据此判断文件内容存在重复模式。AES 从 hash1  派生 IV，不同用户即使密码相同，由于 hash1  不同（受盐值影
响），IV 也不同，相同明文会产生完全不同的密文，更安全。
思考题5
 
问题：如果备份文件在传输过程中某几个比特发生翻转，CRC64 一定能检测出来吗？
参考回答：不一定。CRC64 的检测能力取决于错误模式和 CRC 多项式。CRC64 能检测出所有 1-4 位的突发错
误，以及所有奇数个位的错误，但在极少数情况下（约 2^-64 的概率），错误的文件也可能碰巧通过 CRC 校验。这也
是为什么金融级系统会使用更复杂的校验方案（如 SHA-256 + 数字签名）。
思考题6
 
问题：为什么要用 extern "C"  封装 C++ 的加密库？直接用 C++ 类接口不行吗？
参考回答：C++ 的 ABI 在不同编译器之间不兼容，extern "C"  确保接口使用 C 的命名和调用约定，任何支持 C 
接口的语言（Python、C#、Java 等）都可以调用这个库，提高了代码的复用性和跨语言兼容性。
12. 总结
 
核心知识点
 
1. 对称加密：加密和解密使用相同密钥，适合备份场景
2. 密钥派生：使用 SHA256 + 盐值 将用户密码转换为固定长度密钥
3. CBC模式：每个明文块与前一个密文块异或后加密，避免相同明文产生相同密文
4. PKCS#7补齐：分组密码要求数据长度是块大小的整数倍
5. 两次哈希策略：hash1  用于派生密钥，hash2  用于密码验证
6. 先压缩后加密：压缩利用冗余，加密消除冗余，顺序不可颠倒
7. ABI兼容性：使用 extern "C"  包装 C++ 接口，确保跨编译器兼容
8. CRC64校验：检测文件完整性，区分意外损坏和正常文件

代码设计亮点
 
✅ 统一的加密算法接口 IEncryptionAlgorithm ，DES 和 AES 可互换
✅ 密钥派生函数 saltedSHA256  统一处理密码到密钥的转换
✅ OpenSSL EVP API 自动处理补齐，简化实现
✅ 文件头设计支持算法标识、CRC校验和密码验证
✅ 两次哈希分离密钥派生和密码验证的职责
