2.3 Huffman编码生成
 
规则：左分支标 0 ，右分支标 1 ，从根到叶子的路径即为该字符编码。
以字符串 "ABACCDA"  为例：
字符频率：A:3, B:1, C:2, D:1
构造的哈夫曼树（一种可能形态）：
编码结果：
A: 0
C: 10
B: 110
D: 111
原始字符串 ABACCDA  → 压缩后比特串 0 110 0 10 10 111 0  = 0110010101110 （13 bits）
原始用 ASCII 需要 7×8=56 bits，压缩率 13/56 ≈ 23.2%。

2.6 编码后的比特打包
 
警告：不要用 char  数组存储 '0' / '1'  字符串！那样会使文件膨胀（每个比特占用一个字节）。
正确做法：将比特串按 8 位一组打包成真正的字节（位操作）。
填充问题：Huffman 编码后的比特串长度不一定是 8 的整数倍，最后需要补 0  对齐。

class BitVec {
public:
    BitVec(const std::string &str) {  // str 长度必须为 8
        value = 0;
        int shift = 7;
        for (char c : str) {
            if (c == '1') value |= (1u << shift);
            shift--;
        }
    }
    uint8_t to_uint8_t() { return value; }
};

HuffmanNode* createHuffmanTree(const WordCount& wc) {
    // 小顶堆比较器：频率小的优先
    struct NodeCompare {
        bool operator()(HuffmanNode*& a, HuffmanNode*& b) {
            return a->freq > b->freq;  // 注意：返回 true 表示 a 优先级低于 b
        }
    };
    priority_queue<HuffmanNode*, vector<HuffmanNode*>, NodeCompare> pq;
    for (int i = 0; i < 256; i++) {
        if (wc.table[i] > 0)
            pq.push(new HuffmanNode((uint8_t)i, wc.table[i]));
    }
    while (pq.size() > 1) {
        auto left = pq.top(); pq.pop();
        auto right = pq.top(); pq.pop();
        auto parent = new HuffmanNode(left->data, left->freq + right->freq);

void generateCodeDict(HuffmanNode* root, string code, vector<string>& dict) {
    if (!root) return;
    if (!root->left && !root->right) {
        dict[root->data] = code;   // 叶子节点：存储编码
        return;
    }
    generateCodeDict(root->left, code + "0", dict);
    generateCodeDict(root->right, code + "1", dict);
}

int huffmanDecoding(..., HuffmanNode* root, uint8_t paddingNum) {
    string codecBuffer;
    uint8_t word;
    while (sfFile.readN(&word, 1) > 0) {
        BitVec bv(word);
        codecBuffer += bv.to_string();  // 转成 "0101..." 字符串
        // 边解码边处理，避免 buffer 无限增长
        HuffmanNode* ptr = root;
        for (size_t i = 0; i < codecBuffer.size(); i++) {
            ptr = (codecBuffer[i] == '0') ? ptr->left : ptr->right;
            if (!ptr->left && !ptr->right) {
                targetFile.writeN(&ptr->data, 1);
                ptr = root;
                // 如果剩余比特不够一个最长编码，则前移并跳出
                if (codecBuffer.size() - 1 - i < CODE_LENGTH) {
                    codecBuffer = codecBuffer.substr(i + 1);
                    break;
                }
            }
        }
    }
    // 去掉填充位，解码剩余
    for (int i = 0; i < paddingNum; i++) codecBuffer.pop_back();
    // 继续解码剩余比特...
}

4. LZ77算法原理
 
4.1 核心思想
 
利用数据中重复出现的字符串：当遇到重复片段时，用 （距离，长度，下一个字符） 的三元组代替原始数据。
距离：从当前位置向前回溯多少个字节。
长度：匹配到的重复字符串长度。
下一个字符：匹配结束后紧跟的那个新字符（用于处理边界）。
4.2 滑动窗口模型
 
编码器维护一个滑动窗口，分为两部分：
字典区域：已编码过的数据，作为匹配参考。
前向缓冲区：即将编码的数据，在其中寻找与字典的最长匹配。
4.3 编码示例
 
原始数据：abcabcabc
编码过程（假设窗口足够大）：
1. 光标在 a ，字典为空 → 编码 (0, 0, 'a') ，输出 a 。
2. 光标在 b ，字典 a  无匹配 → 编码 (0, 0, 'b') ，输出 b 。
3. 光标在 c ，字典 ab  无匹配 → 编码 (0, 0, 'c') ，输出 c 。

4.4 解码过程
 
解压时维护同样的滑动窗口，按顺序读取三元组：
如果是 (0, 0, c) ，直接输出 c 。
如果是 (距离, 长度, 下一个) ，从当前窗口向前 距离 位置开始，复制 长度 个字符，再追加 下一个 字
符。
解码是确定性的，不需要额外存储字典。
4.5 滑动窗口大小限制
 
实际实现中，窗口大小有限（如 64KB），因为：
内存有限
过大的窗口导致匹配搜索开销大
距离字段需要定长编码

const char* searchLongestMatch(const char* dictBegin, const char* buffBegin,
                               const char* buffEnd, int& longestMatchLen) {
    longestMatchLen = 0;
    const char* longestMatchBegin = buffBegin;
    int len1 = buffEnd - dictBegin - 1;
    int len2 = buffEnd - buffBegin;
    // 从字典每个位置开始尝试匹配
    for (int i = 0; i <= len1 - len2; i++) {
        int x = i, y = 0;
        while (y < len2 && dictBegin[x] == buffBegin[y]) {
            x++; y++;
        }
        if (y > longestMatchLen) {
            longestMatchLen = y;
            longestMatchBegin = dictBegin + i;
        }

7. 课堂思考题
 
Q1：Huffman编码为什么必须统计Byte频率而不是字符频率？
 
答案：因为文件在内存和磁盘中是以二进制字节流存储的，压缩工具不关心文件的文本编码（ASCII/UTF-8/GBK
等）。按字节统计可适用于任何类型的文件（文本、图片、程序等），具有通用性。
Q2：Huffman编码的码表（dict）是 vector，每个码字是字符串如 "110"，
编码时直接拼接 codecBuffer += dict[word]。这样会不会导致内存爆炸？
 
答案：代码使用 CODEC_BUFFER_SIZE  控制 buffer 大小（8192位），每当 buffer 超过该阈值，就立即打包成字
节写入文件，然后将剩余部分前移。因此内存占用是可控的。
Q3：LZ77中，如果字典中没有匹配，searchLongestMatch  返回的 
longestMatchLen  是多少？rcd  如何编码？
 
答案：无匹配时 longestMatchLen = 0 ，rcd.index  也为 0（因为 longestMatchBegin = buffBegin ），
编码为 (0, 0, next) 。解码时遇到 len=0  且 index=0 ，直接输出 next 。
Q4：LZ77解压时，从字典复制数据可能发生重叠（如 index=1, len=10），
代码如何正确处理？
 
答案：代码用 for (i=0; i<rcd.len; i++) buffBegin[i] = buffBegin[-(rcd.index - i)]; 。当 
index=1  时，依次复制 buffBegin[-1] 、buffBegin[-2] 、...，但由于写入的位置在不断前移，第二次复制时 
buffBegin[-1]  已经是刚写入的新字符，从而实现了重复扩展（如将 "ab" 扩展为 "ababab..."）。这正是 LZ77 的语
义。
Q5：为什么 LZ77 的 FILE_BUFFER_SIZE  要远大于 DICT_SIZE + 
BUFF_SIZE ？
 
答案：因为缓冲区刷新时采用非循环缓冲区设计（将剩余数据移动到头部），如果缓冲区太小，频繁的 memcpy  
会降低效率。较大的缓冲区可以减少刷新次数，提高整体吞吐量。
Q6：如果要实现 DEFLATE（LZ77 + Huffman），在现有框架下如何修改？ 
答案：
1. 先将 LZ77 输出的 (index, len, next)  三元组中的 index  和 len  分别用 Huffman 编码。
2. 构建两个独立的 Huffman 树：一个用于距离值，一个用于长度值。
3. 压缩文件头部需要存储两棵树（或对应词频表）。
4. 解码时先解码出 (index, len, next) ，再用 LZ77 的解码逻辑恢复原始数据。

8. 总结
 
核心知识点
 
1. Huffman编码：
基于频率统计，高频短码
构造哈夫曼树（优先队列）
生成编码字典（递归先序遍历）
位打包 + 填充处理
压缩文件需存储词频表
2. LZ77算法：
基于滑动窗口和重复字符串匹配
编码为 (距离, 长度, 下一个字符)  三元组
解码时重建窗口，流式处理
无需额外辅助信息
3. 工程要点：
使用二进制读写，避免文本模式干扰
位操作打包/解包
缓冲区管理（避免频繁 I/O）
文件头设计（算法标识、校验和）
代码设计亮点
 
✅ 统一接口 ICompressionAlgorithm ，便于替换算法
✅ Huffman 使用优先队列简化建树
✅ 位向量类 BitVec  封装比特 ↔ 字节转换
✅ LZ77 使用非循环缓冲区，内存管理清晰
✅ 完善的错误检查和资源释放
