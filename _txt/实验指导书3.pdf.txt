git reset  也可以返回到之前的节点，但是我们的提交历史不会保留。如果我们将此处的checkout替
换未reset，我们就不能使⽤git checkout master  返回到第⼆次提交的状态，因为master也被重置
到第⼀版。这意味着我们将第⼆版的提交信息完全丢弃了。但是第⼆版与第⼀版之间的差异（reset之前
第⼆版提交的内容）是否被重置，和reset的参数选项有关，下⾯会详细介绍。
5. 丢弃暂存区代码

“code”），此⼩节的更改（即“some mistake”）和第⼆版的提交记录（即“modified code”）都将被丢
弃，且⽆法恢复。
6. 处理错误的commit
查看完状态，我们需要进⾏修改。由于"modified version"有错误，我们需要回退到错误之前，即第⼀次提交
完成的时候。
但是，⽬前我们已经准备要做第四版提交了，使⽤git reset --hard 代价过⾼。怎么办呢？使⽤“--soft”选
项！

git add .       # 将错误的代码提交到了暂存区
git reset --hard    # 丢弃暂存的内容，将⼯作区内⽂件恢复到最近⼀次commit的状态
cat code.cpp    # 发现⽂件返回到第⼆版的状态，为modified code。第⼆版以后未提交的修改（包括
add的修改）均被重置。
# 我们继续进⾏第三次提交,这次我们要写另⼀个⽂件
echo "third code" > code_2.cpp
git add .; git commit -m "third version"
# 准备继续写第四版
echo "four code" > code_2.cpp
# 此时我们发现提交的"modified version"有错误，需要修改
# 做之前我们可以先查看当前的状态
git status      # 查看⼀下当前⼯作区状态
# 信息
On branch master                # 在master分⽀
Changes not staged for commit:  # 存在没有暂存的更改
    (use "git add <file>..." to update what will be committed)
    (use "git restore <file>..." to discard changes in working directory)
            modified:   code_2.cpp # 被修改的⽂件
no changes added to commit (use "git add" and/or "git commit -a")
# 上⾯为git status的信息

git reset HEAD~2 --soft # 将提交历史恢复到第⼀版的时候

=== PAGE 15 ===
补充：git reset 默认为--mixed 模式，此模式与--soft 的区别:
git reset --soft 保留⼯作区代码不变，会将之前的更改⾃动加⼊暂存区，我们使⽤git commit  就
可以将代码状态恢复到reset之前。
git reset --mixed 同样保留⼯作区代码不变，会将之前的更改重置为未暂存的状态，此时直接使
⽤git commit 并不能将之前的更改提交。我们需要⼿动使⽤git add 将需要的⽂件添加到暂存区，随
后再进⾏提交。

5. git fetch 与git pull
在4.模拟B进⾏⼀些代码的提交部分，我们已经了解了在trunk⼯作流如何进⾏简单的多⼈协作开发，以
及遇到冲突该如何处理。此部分为了解性知识，介绍fetch与pull的区别。
参照⼆、git与github的⼯作原理中的原理图，可以了解到git fetch 只是将远程仓库的代码同步到本
地仓库，它并不会影响⼯作区的代码。
只看图或许难以理解git pull ，git pull 做了两件事：⾸先，它将远程仓库与本地仓库进⾏同步，
这点与git fetch 相同；其次，它在同步完成后⽴即将远程仓库的最新节点和本地⼯作区的节点进⾏了
合并提交。合并的⽅式与设置相关，本例中选择的时rebase。
# 提交到本地仓库后，A需要把⾃⼰的代码推送到远程仓库，以便其他⼈看到A的代码、在A提交的代码基础上继续
改进
# 在push之前使⽤pull及时与远程仓库同步是⼀个好习惯
git pull origin main      # 由于A最先完成他的⼯作，此时远程仓库没有别⼈的提交，因此不存在远程
仓库和本地仓库的冲突
git push    # 将本地的代码推送到远程仓库
cd ~/github_test/B_demo # 进⼊B的⼯作区
# B编写⾃⼰的任务代码
echo B_fun_2 > code_2.cpp
echo B_fun_3 > code_3.cpp
git add .; git commit -m "B f_2 f_3" # 提交到本地仓库
# B也需要将⾃⼰的代码提交到远程。为确保⾃⼰是的修改是基于最新版本的，B在push之前最好先做pull操作，
将⾃⼰的代码版本更新到最新。
git config pull.rebase true   # ⾸先设置pull时处理的⽅式，trunk⼯作流建议使⽤rebase模式
git pull origin main        # B提交的时候，远程仓库已经被A更改了，因此pull时会提示冲突
cat code_2.cpp             # 查看冲突的⽂件
<<<<<<< HEAD
A_fun_2
=======
B_fun_2
>>>>>>> 01f9d76 (B f_2 f_3)
echo A_B_fun_2 > code_2.cpp         # 处理冲突
git add . ; git rebase --continue   # 完成rebase
git log     # 可以看到A和B分别进⾏了两次提交
git push    # 将本地的代码推送到远程仓库
