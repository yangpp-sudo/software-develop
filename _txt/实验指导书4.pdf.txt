⼀、makefile介绍
 
makefile规定了整个⼯程的编译规则。⼀个⼯程中的源⽂件不计其数，并且按类型、功能、模块分别放在若⼲个⽬
录中，makefile定义了⼀系列的规则来指定，哪些⽂件需要先编译，哪些⽂件需要后编译，哪些⽂件需要重新编
译，甚⾄于进⾏更复杂的功能操作。makefile中可以指定执⾏各种shell命令。
makefile带来的好处就是——“⾃动化编译”，⼀旦写好，只需要⼀个make命令，整个⼯程完全⾃动编译，极⼤地提
⾼了软件开发效率。 make是⼀个命令⼯具，是⼀个解释makefile中指令的命令⼯具，⼀般来说，⼤多数的IDE都有
这个命令，⽐如：Delphi的make，Visual C++的nmake，Linux下GNU的make。可⻅，makefile都成为了⼀种在
⼯程⽅⾯的编译⽅法。

⼆、makefile规则
 
以下是make的规则的格式：
target: 可以是⼀个⽬标⽂件(*.o)，也可以是⼀个执⾏⽂件，还可以是⼀个标签（label）。对于标签这种特
性，在后续的“伪⽬标”章节中会有叙述。
prerequisites: ⽣成该target所依赖的⽂件或其它target的集合。
command: 该target要执⾏的命令。
这是⼀个⽂件的依赖关系，也就是说，target这⼀个或多个的⽬标⽂件依赖于prerequisites中的⽂件，其⽣成规则
定义在commands中。说⽩⼀点就是:
prerequisites中如果有⼀个以上的⽂件⽐target⽂件要新的话，command所定义的命令就会被执⾏。
这就是makefile的规则，也就是makefile中最核⼼的内容。
make并不管命令是怎么⼯作的，他只管执⾏所定义的命令。make会⽐较targets⽂件和prerequisites⽂件的修改
⽇期，如果prerequisites⽂件的⽇期要⽐targets⽂件的⽇期要新，或者target不存在的话，那么，make就会执⾏
后续定义的命令。
当我们在shell中输⼊make 后，make找到当前⽬录下的Makefile（默认为Makefile或makefile），找到其中的第⼀
个target，并执⾏对应的commands。

五、makefile中的静态模式
 
静态模式可以更加容易地定义多个⽬标的规则，可以让我们的规则变得更加有弹性和灵活。我们还是先来看⼀下语
法：
targets：定义了⼀系列的⽬标⽂件，可以有通配符。是⽬标的⼀个集合。
target-pattern：是指明了targets的模式，也就是的⽬标集模式。
prereq-patterns：是⽬标的依赖模式，它对target-pattern形成的模式再进⾏⼀次依赖⽬标的定义。
这样描述这三个东⻄，可能还是没有说清楚，还是举个例⼦来说明⼀下吧。如果我们的<target-pattern> 定义成 
%.o ，则代表<target> 集合中所有以 .o  结尾的<target> 。⽽如果我们的<prereq-patterns>  定义成 %.c  
，则是对<target-pattern> 所形成的⽬标集进⾏⼆次定义，其计算⽅法是，取 <target-pattern>  模式中的 
% （也就是%.o 中去掉了 .o  这个结尾）代表的部分，并为其加上 .c  这个结尾，形成的新集合。在多数时
候，<target> 是可以省略的，以下是⼀个例⼦：
本实验代码中的⽤法如下：
objects=main.o add.o dec.o mul.o div.o
CC=gcc
CFLAGS=-Wall -O -g 
pragram:$(objects)
   ${CC} $^ -o $@
clean:
   rm *.o pragram
<targets ...> : <target-pattern> : <prereq-patterns ...>
   <commands> 
    ...
%.o : %.c
   gcc -c $< -o $@
# "静态模式+⾃动化变量" 来⽣成 ".o" ⽬标⽂件
# $@代表target的名字，$<代表右侧输⼊的第⼀个名字
# 该规则展开如下：
# ./obj/foo.o : ./src/foo.c
#    $(CXX) -c $(CXXFLAGS) foo.c -o foo.o

六、makefile中的伪⽬标
 
我们的程序代码中，我们提到过⼀个“clean”的⽬标，这是⼀个“伪⽬标”，
正像我们前⾯例⼦中的“clean”⼀样，既然我们⽣成了许多⽂件编译⽂件，我们也应该提供⼀个清除它们的“⽬标”以
备完整地重编译⽽⽤。 （以“make clean”来使⽤该⽬标）
因为，我们并不⽣成“clean”这个⽂件。“伪⽬标”并不是⼀个⽂件，只是⼀个标签，由于“伪⽬标”不是⽂件，所以
make⽆法⽣成它的依赖关系和决定它是否要执⾏。我们只有通过显式地指明这个“⽬标”才能让其⽣效。当然，“伪
⽬标”的取名不能和⽂件名重名，不然其就失去了“伪⽬标”的意义了。
当然，为了避免和⽂件重名的这种情况，我们可以使⽤⼀个特殊的标记“.PHONY”来显式地指明⼀个⽬标是“伪⽬
标”，向make说明，不管是否有这个⽂件，这个⽬标就是“伪⽬标”。
伪⽬标⼀般没有依赖的⽂件。但是，我们也可以为伪⽬标指定所依赖的⽂件。伪⽬标同样可以作为“默认⽬标”，只
要将其放在第⼀个。⼀个示例就是，如果你的Makefile需要⼀⼝⽓⽣成若⼲个可执⾏⽂件，但你只想简单地敲⼀个
make完事，并且，所有的⽬标⽂件都写在⼀个Makefile中，那么你可以使⽤“伪⽬标”这个特性。

⼀、Googletest基础
 
Googletest（通常简称为gtest）是由Google开发的⼀个C++单元测试框架，⽤于编写和运⾏⾃动化测试。它⽀持
各种测试⽅法，包括单元测试、集成测试和功能测试等，并提供了丰富的测试⼯具和测试报告，以帮助开发⼈员快
速、准确地测试和验证代码的正确性和健壮性。
使⽤GoogleTest时，⾸先要编写断⾔，这些断⾔是检查条件是否为真的语句。断⾔的结果可以是成功、⾮致命的失
败或致命的失败。如果发⽣致命故障，则中⽌当前功能；否则程序正常继续。
常⻅定义：
Test Case：Test Case是指⼀个独⽴的测试⽤例，通常测试⼀个特定的函数或⽅法。每个Test Case都是使
⽤TEST 或TEST_F 宏定义的，可以独⽴运⾏和测试。
Test Suite：Test Suite是指⼀组相关的测试⽤例，通常⽤于打包测试⼀个共同的功能或对象。⼀个Test Suite
可以包含多个Test Case。
Test Fixture：当⼀个Test Suite中的多个Test Case需要共享公共的对象和⼦例程时，可以使⽤Test Fixture来
封装共享部分。在使⽤Test Fixture时，必须使⽤TEST_F 宏，其它情况则使⽤TEST 宏。
⼆、assertion、test suite和test fixture
 
1. assertion：“断⾔”是类似于函数调⽤的宏，⽤于判定类或函数的⾏为是否达到预期。当断⾔失败时，
GoogleTest会打印⼀条失败消息。以下两类常⻅的断⾔：
1. ASSERT_*：当断⾔失败时，产⽣致命错误、并终⽌当前函数，包括：ASSERT_TRUE、ASSERT_FALSE、
ASSERT_EQ、ASSERT_NE、ASSERT_STREQ、ASSERT_STRNE等。
2. EXPECT_*：当断⾔失败时，产⽣⾮致命错误，并不会终⽌当前函数。
2. Test Suite：Test Suite是测试的基础，其包含⼀个或多个Test Case。应将逻辑上具有相关性的测试⽤例放到
⼀个Test Suite中。以下是⼀个Test Case的格式
使⽤TEST()宏来定义和命名Test Case。每个Test Case可视为⼀个不返回值的普通C++函数。
在这个函数中，连同您想要包含的任何有效的C++语句⼀起，使⽤各种GoogleTest断⾔来检查值。
测试的结果由断⾔决定；如果测试中的任何断⾔失败（⽆论是致命的还是⾮致命的），亦或测试崩溃，
则整个测试失败。否则成功。
TEST(TestSuiteName, TestName) {
  ... test body ...
}

3. Test Fixture：当⼀个Test Suite中的多个测试需要共享公共对象和⼦例程时，可以使⽤Test Fixture对Test 
Suite进⾏包装，以使⽤相同的数据配置进⾏不同的Test Case测试。其使⽤⽅法如下：
1. 从::testing::Test 派⽣⼀个类。它的主体以protected: 开头，因为我们希望从⼦类访问fixture的
成员。
2. 在类内部，声明您计划使⽤的任何对象。
3. 可实现虚函数virtual void SetUp() ，⽤于Test Fixture中每个Test Case的测试环境的初始化。（在
每个Test Case中最先执⾏。）
4. 可实现虚函数virtual void TearDown() ，⽤于Test Fixture中每个Test Case的测试环境的资源清
理。（在每个Test Case中最后执⾏。）
5. 如果需要，可定义⼀些测试中需要⽤到的公共的⼦例程。
使⽤Test Fixture时，请使⽤TEST_F() ⽽不是TEST() ，因为它允许您访问Test Fixture中的对象和⼦例程：
与TEST() 不同，在TEST_F() 中，第⼀个参数必须是Test Fixture的名称（_F代表“Fixture”）。可认为Test 
Suite和Test Fixture同名。
不幸的是，C++宏系统不允许我们创建⼀个可以同时处理这两种类型测试的宏。使⽤错误的宏会导致编译器错
误。
此外，在test_F() 中使⽤Test Fixture之前，您必须⾸先定义它，否则您将得到编译器错误“虚拟外部类声
明”。
对于⽤test_F() 定义的每个Test Case，GoogleTest将在运⾏时创建⼀个新的Test Fixture，并⽴即通过
SetUp() 对其进⾏初始化，然后运⾏测试，再调⽤TearDown() 进⾏清理，最后删除该Test Fixture。请注
意：同⼀Test Suite中的不同Test Case具有不同的Test Fixture对象。GoogleTest不会对多个Test Case重复使
⽤同⼀个Test Fixture，即⼀个Test Case对Test Fixture所做的任何更改都不会影响其它Test Case。

⼀、认识valgrind
 
Valgrind是⼀套Linux下，开放源代码的仿真调试⼯具的集合。Valgrind由内核以及基于内核的其他调试⼯具组成。

⼀、gprof介绍
 
gprof(GNU profiler)是GNU binutils⼯具集中的⼀个⼯具，linux系统当中会⾃带这个⼯具。它可以分析程序的性
能，能给出函数调⽤时间、调⽤次数和调⽤关系，找出程序的瓶颈所在。在编译和链接选项中都加⼊-pg之后，gcc
会在每个函数中插⼊代码⽚段，⽤于记录函数间的调⽤关系和调⽤次数，并采集函数的调⽤时间。
⼆、gprof使⽤及可视化
 
1. ⽤gcc、g++编译程序时，使⽤-pg参数。如：g++ -pg -o test.exe test.cpp （本项⽬中编译⽐较复杂，
可直接make）
编译器会⾃动在⽬标代码中插⼊⽤于性能测试的代码⽚断，这些代码在程序运⾏时采集并记录函数的调⽤关系
和调⽤次数，并记录函数⾃身执⾏时间和被调⽤函数的执⾏时间。
2. 执⾏编译后的可执⾏程序，⽣成⽂件gmon.out 。
该步骤运⾏程序的时间会稍慢于正常编译的可执⾏程序的运⾏时间。程序运⾏结束后，会在程序所在路径下⽣
成⼀个缺省⽂件名为gmon.out 的⽂件，这个⽂件就是记录程序运⾏的性能、调⽤关系、调⽤次数等信息的数
据⽂件。
3. 使⽤gprof命令来分析记录程序运⾏信息的gmon.out⽂件。如：gprof ./bin/zoo_boom.out gmon.out>

⼀、perf介绍

数级别的采样，从⽽了解程序的性能瓶颈究竟在哪⾥等等。Perf 还可以替代 strace，可以添加动态内核 probe 
点，还可以做 benchmark 衡量调度器的好坏。
