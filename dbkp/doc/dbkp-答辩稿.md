### P5 03 系统设计 · 四层架构 — 0:55–1:16

> 系统分四层：接口层是命令行、服务入口和页面；编排层是引擎、调度和任务队列；
> 引擎层是打包、遍历、压缩、加密；基础层是序列化、哈希和平台适配。
> 两条纪律最关键：系统调用只从 Platform 出去，内核完全不知道 HTTP 的存在。

【备用扩写】这条纪律的实测收益——同一份内核既能被 `bk` 命令行调用，也能被 `bkd` 的线程池调用，两个入口共享 27 个错误码。

### P6 03 系统设计 · 归档格式 — 1:16–1:34

> 归档布局分卷标、载荷区、提交动作三段，记录 512 字节定长、数据块按 512 对齐。
> 两个决定值得说：不设独立尾记录，完整性靠卷标里的长度和 CRC 反推；
> 全程写临时文件，自校验通过才改名。

【备用扩写】「为什么不留尾记录」→ 尾部一旦损坏就整卷不可读；定长卷标 + 反推让截断可判定（`E_TRUNCATED_ARCHIVE`），50 轮稳定性测试目录内 `.tmp` 残留数为 0。

### P7 04 关键技术 · 算法 — 1:34–1:55

> 算法是课程重点。压缩五档、加密三种，AES 的 S 盒是在 GF(2⁸) 上在线算的，不查硬编码表；
> 口令走 PBKDF2，随机源用系统 CSPRNG，拿不到就抛异常、绝不退回弱源。
> 所有算法都对了官方向量，现场跑一次单元自测程序就能验。

## 4. 现场演示动线（60–90 秒，可选）

> ⚠ **演示前必须先在答辩用机上重新构建一次**。本仓的 `bin\bk.exe` / `bin\bk_test.exe` / `bin\bkd.exe` 是**随仓库提交的二进制**，它们是在另一台机器（MinGW-w64 GCC 8.1.0）上编的；在这台开发机 YANG 上直接运行会返回退出码 `-1073741511`（0xC0000135 STATUS_DLL_NOT_FOUND，本机 MinGW 是 GCC 14.1.0，运行时对不上）。已验证：本机用 `C:\mingw64\bin\g++.exe` 编一个最小程序是能跑的，所以**不是代码问题，是拷来的旧二进制问题**。处置：`cd dbkp; mingw32-make -j4`（约几分钟），用本机产物跑完下面三组命令再上答辩。
>
> 因此：本节命令的正确性目前三重保障——① 参数与输出文案逐行读了 `src/main.cpp` / `src/server_main.cpp` / `test/TestFramework.h`；② 数字均抄自《软件测试报告》与 `doc/perf/` 原始记录；③ 尚未在本机实跑（因为跑不起来）。**这一项必须在你们能跑 binary 的终端里补验。**

> **提前 3 分钟准备**：先在一个空闲终端里把 `bkd` 起好、浏览器停在页面上；答辩中只做「跑一条命令 + 点一次界面」。
> 全部命令在 PowerShell 里、`cd dbkp` 之后执行（PowerShell 5.1 用 `;` 分隔，不要用 `&&`）。

**A. 算法正确性与格式自检（约 30″，讲 P7 之后或提问时救场）**

```powershell
bin\bk_test.exe            # 361 项单元用例，含 AES / 3DES / ChaCha20 / Huffman / LZ77 / SHA-256 的官方向量
bin\bk.exe selftest         # 环境与格式自检：平台能力、块大小、crc64、sha256("abc")、超长路径记录往返
```

预期：`bk_test` 末行输出 `[========== ] N tests ran, 0 failed, 0 filtered out`（本轮记录为 361 ran / 0 failed）、退出码 0；`bk selftest` 里 `sha256("abc")` 应等于 `ba7816bf8f01cfea414140de5dae2223b00361a396177a9cb410ff61f20015ad`（已用 Python `hashlib` 校过），`long-path rt : ok`、退出码 0。

【说法要分开】被问「哪个命令验算法」时：算法向量在 `bk_test` 里，`bk selftest` 验的是**格式与哈希**（顺带把环境能力报出来），两条不要说成一条。口头补一句：「测试向量来自官方示例和标准测试集，不是我们自己出的题；AES 还另用一份独立 Python 参考实现做过交叉校验。」

**B. 备份 → 校验 → 篡改必检出（约 40″）**

```powershell
$bk = Join-Path $env:TEMP 'dbkp_defense.dbkp'
bin\bk.exe backup demo-data $bk -a lzhuff -c chacha20 -p 'Demo#2026' --checksum sha256
bin\bk.exe verify $bk -p 'Demo#2026'          # 期望：verify ok，退出码 0
$b = [IO.File]::ReadAllBytes($bk); $b[2000] = $b[2000] -bxor 0xFF; [IO.File]::WriteAllBytes($bk, $b)
bin\bk.exe verify $bk -p 'Demo#2026'; $LASTEXITCODE   # 期望：报错 + 退出码 1
```

话术：「改了一个字节，还原都不用试，校验直接拒绝。改的位置在载荷报 `E_CHECKSUM_MISMATCH`，落在记录头报 `E_INVALID_DATA_RECORD`，落在加密箱卷标报 `E_HEADER_TAMPERED`——三类都是 27 个错误码里的，不是临时拼的字符串。」

**C. Web 控制台（约 30″）**

## 5. Q&A 预案

> 答法模板：**一句结论 → 一句证据出处 → 一句局限**。绝不编没测过的数字。

**Q1 仓库里有 `third_party/googletest`，不是说不用第三方库吗？**
A：约束的范围是压缩、加密、打包、Web 服务这四类核心算法与组件，全部自实现、零依赖。GoogleTest 只在批次 10 作为**第二套测试注册表**引入，用来交叉验证自研迷你框架 `test/TestFramework.h` 的结果，两套都 0 失败；内核产物 `bk/bkd` 里不含任何第三方库。证据：Makefile 的 `gtest` 目标注释明确写了「两种 TEST 宏注册的 .o 不能混用」。

**Q2 AES 档为什么不达标？是不是实现有问题？**
A：按修订前的单一口径「全开 ≥10 MB/s」，AES-256 路径实测 8.7~9.2，确实不达标；瓶颈是手写查表 AES 没有硬件指令加速。我们改的是**判据表达方式**（按算法组合分档，B 档 ≥8）而不是隐藏数字，修订理由和不达标事实都写在《软件测试报告》表 4-2 和 NF-04 说明里。正确性优先：所有算法对官方向量全过。

**Q3 Web 层覆盖率只有 0%～15%，是不是没测？**
A：64.5% 是 gcovr 在 `bk_test` 进程内的统计口径，Web 层（HttpServer / Router / JobManager / Watcher 为 0%，Api 15%）不在该进程内执行，它由真起服务的 48 项 HTTP 冒烟断言 + 44 项前端自检覆盖。我们把这个口径差异如实写在覆盖率表下面，没有拿黑盒结果去凑覆盖率数字。

**Q4 `freeSpaceAt()` 有声明有实现，为什么没调用？**
A：这是我们自己登记的第一条遗留项：写前磁盘预检没有接线，目前空间不足只能在写失败时由 `errno == ENOSPC` 映射成 `E_NOT_ENOUGH_SPACE`，属于「事后报错」而不是「事前拦截」。下一步就是在写出前插一次预检。

**Q5 内存峰值没有上界，实际用会不会爆？**
A：会。单个大文件的编码结果整块驻留，压缩档峰值约为最大单文件的 3~5 倍；本轮 48 MB 混合样本实测峰值工作集 39.3~86.4 MB，量级安全，但要处理大文件必须给编码环节加分块/流式接口。这条也写在《实验结论》未完成项第 1 条。

**Q6 64.5% 覆盖率算高吗？**
A：总量不算高，但结构要说清：核心 19 个文件里 17 个语句覆盖 ≥80%，算法文件 97%~100%；分支覆盖只有 33.5%，说明异常分支还有缺口。分母里被 Web 层和平台适配拉低，这部分归黑盒验收。

**Q7 仓库里为什么有三份互相不一样的性能数据？**
A：差 2~3 倍，来源是机器差异不是算法差异——同一台机器两轮复测偏差 ≤4.2%。从现在起一律以标注了机器名的复测记录（`perf/perf-raw-recheck.txt`）作验收依据，早期的 `perf-raw.txt` 只作历史留档。

**Q8 F11 实时备份到底验过没有？**
A：验过行为、缺一条脚本用例。现有证据是单元测试 `RegressF11` 和控制台走查第 11 步；命令行端到端脚本里没有独立用例，这是第三条未完成项，已定位到 `script/e2e.ps1`。安全设计上是硬的：监听目标落在源目录之内直接拒绝启动。

**Q9 口令和传输安全吗？**
A：存储侧安全——口令经 PBKDF2-HMAC-SHA256 派生，密文用 encrypt-then-HMAC，随机源是系统 CSPRNG，拿不到就抛异常、绝不退回弱源；服务端支持 `--password-sha256` 只存摘要。传输侧不安全且我们主动写明：HTTP 明文、无 TLS，因此默认只绑 127.0.0.1，要开放到局域网必须显式写 `--host 0.0.0.0`。定位是实验与本机使用。

**Q10 AI 写了多少？你们自己会吗？**
A：工具只有 Qoder 的 IDE 内置 Agent，百炼 300 元代金券只当算力渠道，代码里没有调用任何推理 API。AI 的产出我们只当**待核对草稿**：本轮用它批量补白盒用例（用例数 112→361）、跑静态分析和覆盖率、做文档数字对账——对账时改掉了 6 处「看着合理但没有实测支撑」的数字。架构决策、验收标准、真伪判定都是人做的，18 次提交都有三人真实署名。

**Q11 361 项用例会不会是为了凑数？**
A：数字是阶梯式长出来的：112→117→132→152→169→178→361，其中批次 10 一次新增 183 项白盒用例。规矩是每修一条缺陷必须同批补一条同名回归用例（`regress_F1 … regress_F12`），11 条缺陷对应 40 项守故障路径的用例，不是凭空堆量。

**Q12 那个「归档 0 条目也能 PASS」的失败案例说明什么？**
A：说明测试本身也会说谎。根因是 PowerShell 先把通配符展开，脚本断言的是空集合，于是永远通过——典型空断言。整改后所有断言必须绑定可数证据（条目数、退出码、摘要值三者至少之一），这条写进了《软件测试报告》第 3 节。

**Q13 如果重来一次，最先改什么？**
A：先补格式的债。归档格式定下来之后改了两次，每次改都要回归全部用例和文档；其次是判据要一开始就分档写，不要事后用「修订口径」解释不达标。

**Q14 现在能给别人用吗？**
A：能，命令行侧 12 个入口和 Web 控制台都是可用的真程序；限制是三条已登记的遗留项，加上没有做安装包和真正的 TLS。
